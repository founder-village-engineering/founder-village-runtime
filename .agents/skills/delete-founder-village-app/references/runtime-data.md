# Runtime and data removal

## Identify the data boundary

Use the authenticated operator path from the [deployment runbook](../../../../docs/runbooks/DEPLOYMENT.md). Verify the environment and actual PostgreSQL server, database, Hasura source, and any RabbitMQ vhost or bucket. Inspect catalog metadata and aggregate counts without collecting data or credentials in chat or working files. Check live clients, grants, dependencies, reference rows, and object keys against the saved application ID. Use the established Rust catalog for supported operations and a reviewed operator procedure for database or broker changes. Keep the browser Hasura console read-only.

### Frontend or feature on a surviving application

- Keep the shared namespace and Hasura source. A frontend-only retirement may require no PostgreSQL removal. For a feature, enumerate its tables, row predicates, dependencies, related objects, migration history, and shared records. Verify ownership through actual application code and foreign keys. A frontend slug, user, or tenant alone may span multiple features.
- Remove feature metadata, relationships, permissions, and event triggers from the application's `hasura/applications/<application>/tables.json` where applicable. Regenerate with `npm run hasura:generate` and apply through the normal authenticated deployment path. `scripts/hasura.ts` replaces metadata and checks consistency.
- Keep applied files and checksums in `database/migrations/` and `database/applications/<application>/` for every surviving namespace. `packages/database/migrate.ts` rejects missing or changed applied migrations. Keep routine migrations additive and compatible with both API colors. Purge feature rows using reviewed predicates, expected counts, foreign keys, and triggers. Run approved SQL transactions against the verified database, check postconditions, and roll back on unexpected impact. Account for any inert schema retained under the additive migration policy. A physical drop in a surviving database needs an approved schema-retirement procedure that respects the repository's migration rules and deployed and rollback compatibility.

### Dedicated runtime namespace

- Confirm all consumers are retired or migrated and the namespace owns the database, role set, Hasura source, and application-specific migration directory. Remove the application entry from `config/applications.json` and the source-specific metadata, regenerate Hasura metadata, and review any hard-coded references in Compose, Rust rendering, service startup, scripts, and API defaults. Keep `fv_control`, `fv_hasura`, shared roles, and the platform namespaces required by `AGENTS.md`.
- Deploy the namespace removal while the database is still available for recovery. Verify it is absent from live Hasura metadata and the API and admin catalogs and that serving processes, inactive release colors, workers, and scheduled operations have stopped using it. `bin/fv up` and `crates/fv-ops/src/render.rs` derive provisioning from the registry. Reconcile the approved deployment inputs before dropping the database so a restart or rollback cannot recreate it. Remove live migration files from the active tree only after all environments that still migrate or recover that namespace have a compatible signed source or have retired it.
- After the authorized recovery checkpoint, use the trusted operator session to block new connections, handle only sessions for the exact target database, and remove that database. Match dedicated PostgreSQL roles by full name from `crates/fv-ops/src/render.rs` and check their grants and ownership across databases before deleting them. Reconcile app-specific keys in the approved secret catalog and rendered service state. Rendered environment and init files can retain prior keys. Verify removal by key name without printing values. Preserve common credentials and never use Compose volume removal to retire an app.
- Reconcile the retired namespace in shared control state such as `control.administrators.applications`, queued operations, and `control.namespace_status`. Update exact active references while preserving other grants and immutable `control.audit` and checkpoint history. Verify surviving administrator scopes and jobs.

## Jobs, files, and other state

- `packages/queue/` uses `app.schedules`, `app.outbox`, and effect and retry ledgers. Stop the exact producers and consumers, including the domain worker, before removing broker resources. A retired namespace may own `fv.jobs.<application>`, `fv.dead.<application>`, and its binding on the shared `fv.dead` exchange. Reconcile pending, delayed, in-flight, dead-letter, and replay work before deleting these exact queues. A surviving namespace shares those queues across its features, so isolate feature-owned work using validated job provenance. Preserve the common broker, exchange, vhost, and other applications' messages.
- Match app-owned file rows and actual S3-compatible objects before deleting. The runtime file API uses keys under `<application>/<tenant>/`. A whole application prefix is appropriate only if its ownership is exclusive. For a shared application, derive exact object keys from the feature records, verify references, then reconcile objects and rows. Check versions, delete markers, multipart uploads, replicas, retention locks, and outstanding signed URLs when relevant. Keep shared buckets and keys.
- Reconcile app-scoped credentials, generated exports, local import staging, and provider integrations only after the remaining owners have credentials and in-flight work is settled. Keep records required by financial, audit, or retention policies. Record the disposition of protected copies.

## Recovery and proof

- Follow the [recovery runbook](../../../../docs/runbooks/RECOVERY.md) for `bin/fv backup capture`, `bin/fv backup verify`, and `bin/fv backup restore-drill` under the exact environment configuration. pgBackRest captures the whole cluster and WAL. Earlier encrypted, offsite, and immutable copies may retain deleted data. Apply authorized retention and legal holds to the authenticated dependency chain. Avoid app-level edits inside physical archives or deletion of a shared restore chain.
- After purging, check `pg_database` or exact feature row counts and expected tables, compare surviving data and grants, verify Hasura consistency, and check RabbitMQ and object inventory. Capture the post-removal backup and verify the required offsite or immutable copy. In an isolated post-removal restore, explicitly check the retired database or feature records are absent before teardown. The built-in restore drill checks registered databases and removes its container, so arrange this negative check in the isolated restore procedure.
- Record retained backup versions and expiry or review dates. When recovering from before retirement, reapply the retirement and reconcile old credentials, routes, schedules, and jobs before reconnecting the restored environment. Use a retirement-compatible release after irreversible deletion. Access to a previous image alone cannot restore dropped data.
