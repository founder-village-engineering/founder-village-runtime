# Code removal and verification

## Find owners and consumers

- Compare `apps/<slug>/founder-village-app.json` in the frontend checkout with `config/frontends.json`, `config/applications.json`, and `config/local-domains.json` in the runtime. Resolve drift before using those identifiers for provider or data changes. See the [onboarding workspace map](../../create-founder-village-app/references/workspace-map.md).
- Search both repositories and any other in-scope checkout by exact slug, workspace package name, namespace, normalized SQL role or environment prefix, `.fv` hostname, Pages project, custom hostnames, API route prefixes, and any native bundle identifiers. `git grep -l -F -e '<identifier>' --` gives file paths for tracked references. Check relevant untracked work with `git status --short`. Review each match in context and preserve unrelated changes.
- Trace each frontend's roles as an entry point, source of contracts, and supplier or consumer of features. `packages/frontends/index.ts` scopes a composite frontend to its primary application's route group and the route groups of its registered standalone dependencies. If a standalone frontend is removed while its feature survives, first move or decouple the feature registration and canonical contracts so the composition keeps its server-side route and data boundary. If the feature retires too, remove its routes and screens from surviving clients. Resolve any new primary application mapping with the owner before changing a surviving app's data boundary.

## Remove the owned source

- **Frontends.** For a retired frontend, remove its app workspace and its exact links, imports, routes, tests, fixtures, dev and Pages shortcuts, docs, workflow defaults and deployment paths. Regenerate the lockfile through the existing package manager. Check the root `package.json`, Pages workflow, `playwright.config.ts`, and any native CI or publication configuration. Check for older workflows or release refs that could still publish the target. Keep shared tooling and assets used by surviving workspaces.
- **Runtime.** For a retired frontend, remove its entry and exact production, custom, and local origins from `config/frontends.json` and its `.fv` mapping from `config/local-domains.json`. Update surviving consumers' manifest and registry entries together. Remove app-owned routes, versioned API inventory, imports, entitlements, tests, seeds, and canonical `packages/frontend-contracts/<slug>/` only after migrating any surviving consumers. Keep common routing and bearer, tenant, membership, and RLS checks. Follow the [runtime data procedure](runtime-data.md) for namespace and Hasura changes.
- **Generated state.** Remove generated contracts with a deleted workspace. Resync changed surviving workspaces with the runtime synchronizer so obsolete feature copies are pruned and the ownership markers and checksums agree. Coordinate the sibling checkouts on the workstation with `npm run frontend-contracts:sync` and `npm run frontend-contracts:check`. The synchronizer follows current runtime registrations, so verify separately that obsolete frontend workspaces, contract directories, and published copies are gone.

```sh
# From founder-village-runtime, once per affected surviving frontend
npm run frontend-contracts:sync -- --frontends-root ../founder-village-frontends --app <surviving-slug>
npm run frontend-contracts:check -- --frontends-root ../founder-village-frontends
```

Follow public-repository security and the staged scan in each repository before an authorized commit. Treat removing source from the current branch, removing old published artifacts, and any Git history remediation as distinct operations. Historical commits, forks, clones, and signed releases may persist. Coordinate an explicitly authorized history rewrite with the repository owner and the security procedure.

## Roll out compatible code

- When a surviving client still calls the target API, release its compatible client update before removing the serving route. Use the [API versioning runbook](../../../../docs/runbooks/API_VERSIONING.md) for published contract changes and verify the expected response to retired calls from old builds. When the change removes only a frontend, check that its retired origin is denied and that the surviving feature remains accessible to its authorized consumers.
- Check the revisions actually loaded by the serving API, both release colors, workers, admin, `fv-monitor`, and `fv-domain-worker`. Runtime promotion preserves an existing `FV_ADMIN_IMAGE` pin and leaves the previous API color for rollback. Reconcile the admin pin and update host services and their scoped environment files through the operator procedure. Verify the retired namespace is gone from the admin catalog and monitor inventory. Before dropping data required by a prior release, verify a retirement-compatible rollback target or enforce containment that prevents serving the older release until an authorized restore. If updating both colors through promotion, use distinct compatible releases because the active release ID short-circuits a redeploy.
- After a failed promotion or rollback, compare live Hasura metadata with the serving revision. The proxy and worker rollback can leave the metadata applied before cutover in place. Reapply compatible metadata through the authenticated deployment procedure if reconciliation is needed.

## Verify source, local state, and deployed behavior

- Recheck saved identifiers and paths for stale entry points, imports, routes, scripts, deployment triggers, allowlists, and generated state. Review intentional references such as historical migrations or retention records. Run `npm run check` in both repositories and the cross-repository contract check. Verify any deleted frontend cannot be selected by shared Pages tooling. Run the Pages plan for affected survivors.
- For runtime data, worker, or Hasura changes, use the intended `fv-local` fixture under the normal `bin/fv up` and `npm run test:integration` entry points. Check both upgraded state and a fresh install when applicable. Exercise an authenticated surviving route, retired routes without an `Origin` header, and a preflight from each removed origin. Verify the retired application cannot be selected through the generic API or scoped GraphQL relay when a namespace was removed. Use the frontend's `npm run test:e2e` for affected browser flows and verify native flows when applicable. Run `cargo clippy --workspace --all-targets -- -D warnings` if Rust changed.
- Reconcile local proxy routes with `bin/fv local-edge up` when the local edge is in scope, then check `bin/fv local-edge doctor`, the retired HTTPS host, and surviving hosts. CoreDNS can return loopback for any one-label `.fv` name, so verify that the old route and app response have stopped serving. Keep the resolver, shared CA, and Compose volumes. See the [local domains runbook](../../../../docs/runbooks/LOCAL_DOMAINS.md).
- For each authorized live environment, verify the serving signed revision and worker, monitor, and admin health. Verify a surviving session can still perform its intended operation and that the retired entry points are absent or denied. Use the saved production, preview, and custom origins for the hosting probes. When the data inventory changes, verify its physical state and the post-removal backup and isolated restore separately.
